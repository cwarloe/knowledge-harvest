# Contributing to Knowledge Harvest

Thank you for your interest in contributing!  By sharing your expertise, you help us preserve and disseminate tacit knowledge throughout the organisation.

## How to contribute

Use the smallest evidence record that lets someone understand and verify the work. A GitHub issue is useful for a problem that needs discussion, but is **not mandatory** when an approved workstream already defines the scope and its pull request records the acceptance evidence. Do not open a duplicate issue solely to satisfy a ceremony.

### Preauthorized, low-risk maintenance

For a change already within an owner's approved workstream, such as an internal test, deterministic validator, typo, documentation correction, or non-sensitive bug fix:

1. Create a descriptive branch; an issue number is optional.
2. State the expected behavior, affected files, and how it will be checked in the pull request. Link an existing issue if one is relevant.
3. Make the smallest change, keep the source material and existing work intact, and add or run relevant tests. Explain *why* in the commit message.
4. Obtain independent technical scrutiny when the change's risk or complexity warrants it; fix substantive findings. Never claim an AI review is a GitHub team-member approval.
5. Merge a clean, reviewed-as-appropriate pull request after its required CI checks pass, provided no repository protection or explicit owner-review requirement blocks it. The preauthorization covers this routine technical merge; do not request the owner's approval again for each step.

### Work that still requires a decision

Open an issue or decision record and ask the accountable owner before starting or merging changes to:

- Client recordings, credentials, private or identifiable information, access permissions, retention, or the application's security/privacy posture.
- Real client pilots, changes to employee decision rights, expert guidance, or conclusions about workplace competence.
- External outreach, spending, deployments that expose new public content, business strategy, pricing, or legal/regulatory commitments.
- Any scope or risk not covered by the prior authorization, or a stop-the-line finding that the agent cannot safely resolve.

Do not bypass protected-branch requirements or present passing tests as proof that an expert's decision rationale is correct. The [capability-transfer framework](docs/capability-transfer/README.md) keeps its own expert, supervisor, and owner evidence gates for real work.
